# SmartFactory AI — Security Setup & Migration Log

> This document details every step taken to audit, secure, rebrand, and retrain the AI model module before integrating it into the SmartFactory project.

---

## 1. Context

The SmartFactory project (Sprint 8) required an AI module for predictive maintenance — fault classification and anomaly detection on industrial sensor data (Temperature, Vibration, Current, RPM).

A candidate open-source repository (`motor-health-monitor`) was identified on GitHub. It used the same sensor types, the same ML approach (RandomForest + IsolationForest), and provided MQTT integration — making it a strong fit.

However, **no external code should be trusted blindly**, especially ML repositories that contain:
- Serialized model files (`.joblib`, `.pkl`) that can execute arbitrary code on load
- Python scripts with network access
- CI/CD workflows that run automatically
- Docker configurations that spin up services

**Decision:** Download the ZIP (no `.git` clone), inspect everything before running anything, and rebuild from scratch.

---

## 2. Security Audit

### 2.1 Full File Scan (47 files)

Every file in the repository was read and analysed for:
- Malicious code patterns (`eval`, `exec`, `subprocess`, `os.system`, obfuscated strings)
- Unsafe deserialization (`pickle.load`, `joblib.load` from untrusted sources)
- Hidden network calls (unexpected HTTP requests, data exfiltration)
- CI/CD risks (GitHub Actions workflows that could run on push)
- Docker risks (containers with elevated privileges or external image pulls)

### 2.2 Audit Results

**No malicious code was found.** The repository was a legitimate educational/research project. However, several security risks existed:

| Risk | Severity | File(s) |
|---|---|---|
| Pre-built `.joblib` model files | **HIGH** | `models/fault_classifier_rf.joblib`, `models/anomaly_detector_if.joblib` |
| GitHub Actions CI workflows | MEDIUM | `.github/workflows/*.yml` |
| ESP32 firmware (unnecessary) | LOW | `firmware/` directory |
| Docker auto-start config | MEDIUM | `docker-compose.yml` |
| Outdated pinned dependencies | LOW | `requirements.txt` (numpy 1.26.4 incompatible with Python 3.13) |

### 2.3 Why `.joblib` Files Are Dangerous

Python's `joblib.load()` (and `pickle.load()`) deserialize objects by **reconstructing Python objects from bytecode**. A malicious `.joblib` file can:
- Execute arbitrary shell commands when loaded
- Install backdoors, keyloggers, or ransomware
- Exfiltrate data over the network
- Modify other files on disk

**This is not theoretical** — it is a well-documented attack vector in the ML community. The only safe approach is to either:
1. Never load `.joblib`/`.pkl` files from untrusted sources, OR
2. Delete them and retrain models from your own data

**We chose option 2.**

## 4. What Was Rewritten

Every Python file was **rewritten from scratch** to:
1. Use `smartfactory_ai` package name (not `motor_monitor`)
2. Use SmartFactory's 4-sensor schema (not the original 6-channel vibration schema)
3. Match SmartFactory MQTT topics (`factory/machines/{machineCode}/{sensorType}`)
4. Match SmartFactory status labels (`normal`, `degradation`, `anomaly`, `failure`)
5. Integrate with the Spring Boot backend REST API

### 4.1 Core Package (`src/smartfactory_ai/`)

| File | What It Does |
|---|---|
| `__init__.py` | Package metadata, version 1.0.0 |
| `config.py` | YAML config loader with dataclasses (MqttConfig, FeatureConfig, ThresholdConfig, StorageConfig, SimulationConfig, BackendConfig) |
| `schemas.py` | 4-sensor input validation (temperature, vibration, current, rpm), type coercion, status normalization |
| `features.py` | Feature extraction — 22 statistical features from sliding windows (mean, std, max, min, slope, range, rms, peak-to-peak, crest factor, skew, kurtosis, zero crossings) |
| `predict.py` | FaultPredictor class — loads trained models, runs inference, returns PredictionResult (label + confidence + anomaly score) |
| `mqtt_client.py` | MQTT connection helpers using paho-mqtt v2 API |
| `storage.py` | CSV append utilities for readings and alerts |

### 4.2 Scripts (`scripts/`)

| `run_inference_subscriber.py` | Subscribes to MQTT, buffers per-sensor messages into unified snapshots, runs prediction, publishes alerts |
| `collect_mqtt_to_csv.py` | Subscribes to MQTT, saves unified readings to CSV for offline analysis |

## 5. Safe Environment Setup

### 5.1 Isolated Python Virtual Environment

```bash
cd health-monitor-model
python -m venv .venv
.venv\Scripts\activate
pip install --upgrade pip
pip install -r requirements.txt
pip install -e .
```

The venv ensures no system-wide Python packages are affected. All dependencies are installed from PyPI (Python Package Index) — the official, audited package repository.

## 6. Model Retraining (From Scratch)

### 6.1 Training Data Generation

```bash
python scripts/generate_training_data.py --output data/training_data.csv --rows 12000
```

- **11,409 rows generated** (591 dropped by 5% simulated packet loss)
- Data covers all 4 statuses: `normal`, `degradation`, `anomaly`, `failure`
- Sensor values match SmartFactory's IoT simulator targets
- Gaussian noise + sinusoidal drift for realism
- No external data sources — everything is self-generated

## 7. What Was NOT Done (By Design)

| Action | Why Not |
|---|---|
| `docker compose up` | Not needed — we have our own Mosquitto broker. Docker was never started. |
| Loading original `.joblib` files | **Deleted before any code execution** — the core security measure |
| Running original publisher's scripts | All scripts were rewritten before execution |
| Cloning with `git` | Used ZIP download — no git history, no remote tracking |
| Installing TensorFlow | Not used in our architecture (RandomForest + IsolationForest only) |
